### TLS and connection bounds

Neon requires secure connections and documents stronger certificate/channel-binding options. The installed native Prisma 6 connector documents `sslmode=disable|prefer|require` and `sslaccept=strict|accept_invalid_certs`; its certificate-acceptance default is permissive. Therefore the reviewed configuration proposal explicitly requires **`sslmode=require&sslaccept=strict`**, retaining other compatible Console parameters. Do not blindly substitute a different client's `sslmode=verify-full` recipe or remove certificate checks to clear a connection error. Channel binding is supported in the connector's documented URL options, but actual enforcement against Neon was not tested. [Neon secure connections](https://neon.com/docs/connect/connect-securely), [Prisma 6 PostgreSQL TLS/reference](https://www.prisma.io/docs/orm/v6/overview/databases/postgresql).

The disposable TLS test verified: a plaintext-only server is rejected when TLS is required; an untrusted self-signed server certificate is rejected with strict validation; the same server succeeds with its test certificate explicitly trusted, and `pg_stat_ssl` reports TLS. These are actual native-engine tests. They do **not** establish Neon's hostname/certificate chain, channel binding, Docker trust store, egress or pooler behavior. No insecure certificate acceptance was configured for a production target.

Prisma maintains its own pool inside Neon pooling. Select a finite connection budget from the actual Neon compute allowance, VPS process/replica count and measured traffic; do not multiply the CPU-derived default across replicas without accounting for the total. Connection activation can outlast a short cold-start timeout. Retain finite connection/pool waits and evaluate a finite statement/socket timeout against real latency before approving operational settings. No arbitrary production pool size or timeout was installed. The five-second private readiness deadline is deliberately conservative; warm/retry before interpreting a cold-start failure as persistent incompatibility. [Neon Prisma timeout guidance](https://neon.com/docs/guides/prisma).

## 7. AUD-013 — Submission abuse, availability and privacy

**Existing local controls: VERIFIED NO CHANGE JUSTIFIED. Residual operational exposure: RISK DECISION REQUIRED.** No new rate limiter, CAPTCHA, external service, fingerprint, account requirement or student/IP tracking was introduced.

The unchanged `server/utils/submission-security.ts:1`, `submission-service.ts:53` and `submission-http.ts:1` enforce strict JSON/encoding, 32KiB claimed and streamed limits, fatal UTF-8 decode, ten-second body read timeout, strict bounded Zod fields, a honeypot, configured Origin/fetch-site checks, at most 16 process-local in-flight requests, and finally-released slots. The unique per-form UUID request key preserves retry identity and rejects altered same-key details; the frontend suppresses pending duplicate requests and confirms success only after storage. Tests cover malformed bodies, slow/large/aborted reads, concurrency saturation/release, database failures and retry conflicts. Real DB verification confirms the unique constraints and committed rows.

These controls are proportionate defenses for a small public enquiry form. Their limits are material:

- Origin protects browser cross-site submission, not caller identity; bots can omit/spoof it. The honeypot can be left empty. No authentication is implied.
